# MOE-NEW-HYPOTHESES.md — новый пул гипотез ускорения Tiel (поиск 2026-10-02)

**Назначение.** Рабочий список [MOE-VIABLE-HYPOTHESES.md](MOE-VIABLE-HYPOTHESES.md)
почти исчерпан: после №7 и порога op offload пять гипотез подряд не вышли из
шума. Здесь собраны новые идеи из статей, issue и PR апстрима и чужих форков,
а также из чтения кода `llama-tiel/` и уже снятых логов. **Всё здесь — гипотезы**
по правилу 2. Пометки как в журнале:

- **замер** — есть строка в журнале или лог в `bench-logs/`;
- **код** — прочитано в исходниках форка, ссылка на строку;
- **расчёт** — арифметика;
- **не проверено** — чужое число или чужое железо.

**Нумерация.** Номера продолжают общую (№16 и дальше) и идут по рангу. Так
проверенную гипотезу можно перенести в рабочие или отклонённые, не меняя
номера.

**Отбор.** Гипотезы, меняющие выход модели, сюда не входят: ни меньше
экспертов, ни слабее квант, ни приближения. Допустимы два вида изменений.
Первый — побитово тот же выход. Второй — та же математика с другим порядком
сложений; это проверяется эталонами `bench/tiel_reference.py` и KLD, как форк
против 10826. Известные методы, которые меняют выход, перечислены в конце
только для справки, чтобы их не искать заново.

**Сортировка.** Главный ключ — ожидаемый эффект на реальной нагрузке:
кодовый агент, длинный контекст, ходы по 100–3000 новых токенов. Эффект
считается как вероятность, умноженная на размер выигрыша. При близком
эффекте выше то, что дешевле проверить. У каждой гипотезы есть **фильтр** —
шаг, который закрывает её до серьёзной работы.

## Опора для расчётов

TG, короткий контекст (S0-03, S0-04; 10826, на форке не перемерено):

| часть | мс/токен |
|---|---|
| CPU: эксперты, 586.25 MiB на 33.5 MiB/мс | 17.5 |
| GPU: матвеки, 2038.5 MiB на 216.7 MiB/мс | 9.4 |
| GPU: хвост ~1180 мелких ядер | 3.65 |
| копии (130 штук), запуски (41 сплит), ожидания | 3.9 |
| **токен** | **33.6** |

Остальное:

- **Prefill 28K:** на ubatch ≈ max(заливка ~3.0 с, счёт ~2.3–3 с) плюс хост.
  K=2 — 1079 t/s, K=3 — 1141 (PF-03/04).
- **Порог (floor):** 39 новых токенов — 989–1069 мс, 4 токена после отката к
  контрольной точке — **465 мс** (`bench-logs/tiel-prefetch/pf2.log`, форк).
  Из них ~0.29 с — резерв планировщика от backend-сэмплинга, которого запрос
  с грамматикой не платит (№18): у агента 4-токенный ход ~0.12 с, floor
  ~0.75–0.85 с.
- **Глубина:** TG 30.1 @6K → 25.8 @46K (BASE-01). На 100K f16 даёт 24.3 t/s,
  q8_0 — 20.5; это старый замер из комментария в коде, не перемерен.
- **VRAM, q8_0 / ub 4096 / `-np 1`:** `CUDA0 compute` 2028 MiB,
  `CUDA_Host compute` 1088 MiB, KV 1360 MiB, рекуррентное состояние
  62.8 MiB на последовательность (`bench-logs/no15-hot/sched-off.log`,
  `bench-logs/h2-prefill-xfer/buffers-lv4.server.log`).
- **Форма Tiel:** внимание 16 Q-голов на 2 KV-головы (GQA 8), D = 256 —
  выведено из размеров `attn_q` (17 825 792 Б) и `attn_k` (1 114 112 Б) в
  логе загрузки. GatedDeltaNet `head_k_dim` = 128.

## Шаг 0 — реплей агентных сессий (инструмент, не гипотеза)

От нагрузки зависят пять гипотез: №16, №18, №19, №20 и №30. Решают доля
«копирующего» вывода, число новых токенов на ход и совпадение префикса между
ходами. `sweep_bench.py` этого не видит: TG там снимается на `prompt_real.txt`
с `top_k 1` без grammar, а prefill — одним промптом на 28K.

Нужен харнесс, который проигрывает записанные запросы настоящего агента
против сервера. Тело `/v1/chat/completions` берётся целиком, с tools и
grammar. Для каждого хода меряются TTFT, t/s генерации и число **реально
пересчитанных** токенов. Записывать можно прокси-логгером между агентом и
сервером или `--log-file` с `-lv 4`. Метрика для этих гипотез — суммарное
время ходов на одном и том же реплее, baseline первым и последним, как в
протоколе.

## ~~Ранг 1~~ · №16 (проверена). Бесчерновая спекуляция на «копирующих» участках агента

> **Проверено 2026-10-02, шаги 1–2 — подтверждена на копировании.** Сток
> форка: `ngram-mod` +26…37 % TG на копирующем промпте (порог закрытия 10 %).
> Патч `need_n_rs_seq()` (снимки в VRAM, `probe/no16-ngram-rs`): +33 %
> (n-max 4) … **+55 %** (n-max 16), свободный текст в шуме, prefill и floor
> без изменений, выход — ближние ничьи (запас 0.007–0.60). Цена — 62.8 MiB
> VRAM на снимок. Шаг 3 (реплей агента) не сделан.
> Строки NG-01…16 в журнале CLAUDE.md.
>
> **Дополнено 2026-10-02 (NG-17…32):** n-max 4 со снимками влезает в обе
> рабочие конфигурации — +34…36 % на копировании, +54…68 % на 90K, prefill не
> хуже. **С 2026-10-02 включено в лаунчере.** На глубине каждый раунд платит
> перевод KV в f16 (FA2 подтверждена, FA-17…19) — см. №39.

**Суть.** Кодовый агент много копирует из контекста. `old_string` в Edit
берётся дословно из файла, Write переписывает файл с мелкими правками,
повторяются пути, имена и куски вывода. Черновик из n-грамм контекста ничего
не стоит: нет draft-модели, нет налога на prefill, нет VRAM под драфтер. В
форке это уже есть: `--spec-type ngram-mod | ngram-map-k | ngram-map-k4v |
ngram-simple | ngram-cache` (**код**, `common/arg.cpp:4259–4373`). Это не тот
случай, что отклонённые п. 1: там платили prefill за draft-контекст.

**Почему у других не вышло.** На RTX 3090 с Qwen3.6-35B-A3B целиком в VRAM
ngram-mod дал −6…−7 % при acceptance 100 %, ngram-cache — −13 % (**не
проверено**, [hackmd][hackmd]). Причин видно две, и обе у нас другие или
устранимы:

1. **Черновики по умолчанию длинные:** `n_min 48`, `n_max 64`. Верификация
   49–65 токенов читает почти всех экспертов слоя. Длину черновика выбираем
   мы, и её цену можно посчитать (ниже).
2. **Контрольные точки рекуррентного состояния (код).** Снимки состояния в
   VRAM для отката (`n_rs_seq`) форк включает только для MTP, EAGLE3, DFlash
   и DSpark — `need_n_rs_seq()` в
   [common/common.h:396](../llama-tiel/common/common.h:396). Для ngram-типов
   сервер на каждом раунде черновика делает `ckpt.update_tgt(...,
   PARTIAL_ONLY)`, если `draft.size() > n_rs_seq`
   ([server-context.cpp:3069](../llama-tiel/tools/server/server-context.cpp:3069)).
   Это копия на хост всего рекуррентного состояния: 62.8 MiB, размер
   контрольной точки Tiel по логам. Через pageable-вектор это ~10–20 мс на
   раунд плюс обратная копия при отказе — выигрыш съедается целиком.

**Расчёт** (от S0). На шаге с k черновыми токенами GPU-часть и накладные
(16.1 мс) платятся один раз. CPU-часть пропорциональна объединению экспертов
по k+1 токенам: при независимой маршрутизации U(n) = 256·(1 − (1 − 8/256)ⁿ).

| k | CPU, мс | шаг, мс | на токен, если всё принято | Δ TG |
|---|---|---|---|---|
| 1 | 34.5 | 50.6 | 25.3 | +33 % |
| 3 | 66.7 | 82.8 | 20.7 | +62 % |
| 8 | 138.5 | 154.6 | 17.2 | +95 % |

- **Потолок ~1.9×:** CPU-часть не амортизируется.
- **Таблица — худший случай.** По H2-P3 39 соседних токенов промпта задели
  34.5 % экспертов, а формула даёт 71 %: соседние токены делят экспертов.
- **Ошибка дорогая.** Каждый отвергнутый черновой токен стоит до ~17 мс, так
  что совпадение должно быть длинным, а черновик — коротким. При вероятности
  принятия p на токен и k = 3 безубыточность около p ≈ 0.7.
- **Шины в верификации нет.** Батч меньше 128 токенов идёт CPU-путём
  (`GGML_OP_OFFLOAD_MIN_BATCH=128`).

**Выход.** Не меняется. При greedy выход тот же; численно батч k+1 может
отличаться от батча 1, это проверить эталонами. При сэмплинге распределение
сохраняется: черновой токен принимается, только если сэмплер цели выбрал его
же.

**Как проверять.**
1. **Фильтр, без сборки.** Копирующий промпт («перепиши этот файл на ~3K
   токенов с одной правкой») и свободный (`prompt_real`), greedy. Сравнить
   baseline с `--spec-type ngram-mod --spec-ngram-mod-n-match 12
   --spec-ngram-mod-n-min 2 --spec-ngram-mod-n-max 8` и с `ngram-map-k`
   (`size-n` 8–16, `size-m` 4–8, `min-hits` 1/2). В логе смотреть acceptance и
   строки `created speculative checkpoint`. Свободный промпт показывает цену
   на участках без совпадений.
2. **Патч в одну строку.** Добавить ngram-типы в `need_n_rs_seq()` с
   `n_rs_seq = min(n_max, 3…4)` и повторить п. 1. Каждый снимок стоит
   62.8 MiB VRAM — место для них даёт №21.
3. **Реплей агентных сессий** (шаг 0): итог по времени ходов.
4. **Расширения, если выигрыш есть.** Суффиксное дерево по всем прошлым
   ответам: SuffixDecoding — до 5.3× на агентных нагрузках, ~20 мкс на
   черновой токен (**не проверено**, [SuffixDecoding][suffix]). Длина
   черновика по ожидаемой цене объединения экспертов, как в EcoSpec
   ([EcoSpec][ecospec]). Ngram поверх MTP — issue #23184 закрыт без
   реализации ([#23184][i23184]).

**Закрывается, если** на копирующем промпте при коротких черновиках и
снимках в VRAM выигрыш меньше 10 %.

## ~~Ранг 2~~ · №17 (проверена). FA-декод для q8_0 KV без группировки GQA: TG на глубоком контексте

>

**Посылка (код).** На Ampere при квантованном KV и одном токене выбирается
vec-ядро ([fattn.cu:650](../llama-tiel/ggml/src/ggml-cuda/fattn.cu:650)).
Оно запускает отдельный блок на каждую Q-голову и читает K/V заново для
каждой из восьми голов группы
([fattn-vec.cuh:106](../llama-tiel/ggml/src/ggml-cuda/fattn-vec.cuh:106)).
Для f16 KV на той же карте выбирается MMA с группировкой GQA (`ncols2`,
[fattn.cu:660](../llama-tiel/ggml/src/ggml-cuda/fattn.cu:660)): KV читается
один раз на группу.

**Посылка (числа).**
- **Байты.** KV на токен контекста по 10 слоям — 10.9 КБ при q8_0 и 20.5 КБ
  при f16. На 100K шаг читает 1.09 и 2.05 ГБ, по 239 MiB/мс это ≈ 4.4 и
  8.2 мс (**расчёт**).
- **Старый замер из кода.** На 100K f16 добавляет к короткому контексту
  ~7.6 мс — у потолка. q8_0 добавляет ~15 мс — примерно в 3.5 раза хуже
  потолка.
- **BASE-01** даёт то же: 6K → 46K +5.5 мс при расчётных 1.7.
- **AMD.** На RDNA то же явление описано как упор в инструкции, а не в
  память: q8_0 276 ГБ/с против 615 у f16 на KV 102400 (**не проверено**,
  чужое железо, [rdna#45][rdna]).

**Расчёт.** Ядро для q8_0 с группировкой GQA у потолка памяти даст на 46K
~−3.5 мс (+11 % TG). На 100K это ~−10 мс: 20.5 → ~26.5 t/s, +30 % к q8_0 и
+9 % к f16.

**Почему важно.** Агент работает на глубине 20–100K. Заодно снимается KV1:
q8_0 — конфигурация с лучшим prefill (1079 против 564 t/s, PF-03/LF-03), но
сейчас она проигрывает f16 по TG на глубине.

**Выход.** Математика та же; порядок сложений в онлайн-софтмаксе может
отличаться. Проверить эталонами и KLD.

**Как проверять.**
1. **Фильтр, без сборки.** `llama bench -d 8192,32768,65536,100000 -n 64` на
   форке с рабочими флагами, q8_0 против f16. Nsight на одном прогоне: время
   `flash_attn_ext_vec` против байт KV. Если q8_0 и так у потолка — закрыть.
2. **Ядро.** В `fattn-vec.cuh` обрабатывать в одном блоке все Q-головы одной
   KV-головы, как `ncols2` у MMA. Альтернатива — MMA-ядро, распаковывающее
   q8_0 в shared-память без промежуточного f16-буфера. Сначала поискать это в
   апстриме после `dcd387a41`.

**Как проверять** (только запуски, без сборки):

## Ранг 4 · №39. Внимание для пакета проверки черновиков без перевода KV в f16

*Добавлена 2026-10-03 по замеру FA2 (FA-17…19,
[bench-logs/fa2-verify/results.md](../bench-logs/fa2-verify/results.md)).*

**Посылка (код).** На Ampere при квантованном K/V vec-ядро берётся только
для одного токена
([fattn.cu:654–657](../llama-tiel/ggml/src/ggml-cuda/fattn.cu:654)). Пакет из
2–5 токенов — проверка n-gram-черновика (№16, в лаунчере с n-max 4) — уходит
в MMA. Перед ним `launch_fattn` переводит всю заполненную часть K и V каждого
слоя в f16 ([fattn-common.cuh:1031–1091](../llama-tiel/ggml/src/ggml-cuda/fattn-common.cuh:1031)).
В `fattn-mma-f16.cuh` квантованного K/V нет вовсе.

**Посылка (замер, 65K, рабочий бинарь, группа 8).** Цена внимания за проход:

| проход | K/V → f16 | ядро | всего |
|---|---|---|---|
| 1 токен | — | vec 4.38 мс | 4.38 мс |
| 2 и 4 токена | **7.53 мс** (×20, 273 ГБ/с) | MMA 4.92–4.98 мс | 12.45–12.51 мс |

- **Перевод упирается в DRAM:** 102.8 MB за запуск при пике ~288 ГБ/с.
  Ускорить его нельзя, можно только убрать.
- **MMA на f16-копии тоже упирается в DRAM:** 1.34 GB за 4.92 мс,
  272 ГБ/с. На байтах q8_0 (0.71 GB) с той же скоростью — ~2.6 мс
  (**расчёт**).

**Расчёт.** Цена растёт линейно с глубиной (×1.37 на 89 795). Копирование
на 90K со спекуляцией — 38.04 t/s (FA-08), mean len 4.88 (NG1), раунд
≈ 128 мс.

| вариант | внимание за раунд @90K | раунд | копирование @90K |
|---|---|---|---|
| сейчас | 17.1 мс | 128 мс | 38.0 t/s |
| a) vec с группой и 2–5 колонками токенов, KV читается один раз | ~6 мс | ~117 мс | **~41.8 t/s, +10 %** |
| b) MMA, распаковывающее q8_0 в shared | ~3.6 мс | ~114 мс | **~42.6 t/s, +12 %** |

На 65K +6…9 %, на свободном тексте черновиков мало — около нуля, на
коротком контексте — ноль. Вариант (b) ускоряет и одиночный декод:
~2.6 мс против 4.38 у vec на 65K, это и есть приз №40.

**Попутно.** Те же 7.5 мс @65K платит любой проход из ≥ 2 токенов: короткий
ход пользователя и каждый ubatch prefill на глубине. Там это незаметно —
ход ~1 с, ubatch ~3 с.

**Риск.**
- (a): у vec с группой 8 уже 252 регистра на 8 колонок. С 2–5 токенами
  колонок станет 16–40 — нужна другая раскладка: Q в shared, меньше
  развёртки.
- (b): новое ядро масштаба апстрима, хотя тайлинг MMA уже есть и меняется
  только загрузка тайла K/V.

**Выход.** Порядок сложений: проверять эталонами (`tiel_reference.py`) и
`spec_divergence.py`, как №16 и №17.

**Как проверять.**
1. **Сначала поиск.** Нет ли в апстриме после `dcd387a41` MMA-FA с
   квантованным K/V или vec с `ncols1 > 1` для Ampere: issue, PR, чужие форки.
2. **Микробенчмарк.** `test-backend-ops perf -o FLASH_ATTN_EXT` с формами
   Tiel: D 256, GQA 8, n_kv 65536, q8_0, 1/2/5 токенов. Сначала сток — так
   видна цена перевода внутри op.
3. Ядро, затем свип `deep` со спекуляцией (как FA-08) и эталоны.

**Закрывается**, если ядро на 2–5 токенах @65K не опускается ниже ~6 мс
(экономия < 6 мс за раунд, < 5 % на копировании).

> пересчитывает весь прошлый ответ плюс 4 токена: 918 из 4285 токенов, по
> расчёту ~1 с на ход в среднем и до 2.8 с на коротких ходах: лишние токены
> перебрасывают ход через порог 128 на путь с заливкой экспертов. Какой клиент у пользователя — не
> проверено.

**Посылка (код).** Рекуррентное состояние гибридной модели частично не
откатывается. При расхождении нового промпта с кэшем сервер восстанавливает
контрольную точку и пересчитывает всё после неё. Контрольные точки ставятся
у конца промпта (`n_ubatch + 4` и 4 токена до конца) и у последнего
user-сообщения; прочие — не чаще чем раз в 8192 токена
([server-context.cpp:3550–3628](../llama-tiel/tools/server/server-context.cpp:3550)).

**Гипотеза.** Шаблон может перерисовывать прошлый ответ ассистента не теми
же токенами, что сгенерировала модель: вызовы инструментов заново
сериализуются из JSON, рассуждения могут переформатироваться. Тогда каждый
ход пересчитывает весь предыдущий ответ — сотни или тысячи токенов, по
данным P2 это ~3 с. `preserve_reasoning` включён по умолчанию (лог
загрузки), но совпадение вызовов инструментов не проверялось.

**Как проверять.** На реальной сессии с `-lv 4` для каждого хода выписать
`n_past`, `f_keep`, строки `restored context checkpoint` и число реально
пересчитанных токенов против числа новых. Если пересчёт систематически
больше новых токенов — чинить в клиенте (отдавать ответ ассистента как
есть) или в сервере. Для агентов с субагентами отдельно проверить, что
переключения контекстов в одном слоте ловит `--cache-ram`.

**Закрывается**, если пересчёт на ходе равен числу новых токенов.

## Ранг 7 · №21. Убрать материализованную маску внимания

**Посылка (код + лог).** Маска — входной f16-тензор `[n_kv, n_ubatch]`
([llama-graph.cpp:29](../llama-tiel/src/llama-graph.cpp:29)). Резерв
считается на худший случай: n_kv = 131072, n_ubatch = 4096 — это
**1024 MiB**. Входы лежат на хосте, и `CUDA_Host compute buffer =
1088.41 MiB` — почти целиком маска.
- **Копия на карте.** Она, видимо, занимает ~1 GiB из 2028 MiB CUDA
  compute-буфера на всё время графа, потому что нужна всем 10 слоям
  внимания. Это **расчёт**, проверить дампом.
- **Хостовая работа.** На каждом ubatch хост строит маску (47–61 мс на 28K,
  замер в №12) и копирует её на карту. На 100K это примерно в 3.5 раза
  больше.

**Что даст освобождённый ~1 GiB** (ничего из этого не мерилось):
- K=3 без риска пейджинга (P1): +5.8 % prefill к K=2 (PF-04 против PF-03);
- снимки рекуррентного состояния для №16 и MTP, по 62.8 MiB каждый;
- draft-контекст MTP без переполнения (№24);
- `-ub 6144`/`8192`: вдвое меньше заливок на токен. Это дешёвый аналог №12,
  ждать стоит в пределах его +3.5 %;
- prefill на глубине: −5…8 % на ubatch при 100K за счёт хостовой сборки
  маски и её H2D.

**Готовые реализации** (обе в чужих форках, не в апстриме):
- **Битовая маска:** 16 ячеек на элемент I16, CUDA vec/tile/mma и CPU;
  заявлено «побитово как f16-эталон» ([torad-labs#6][maskbits]).
- **Компактная маска:** позиции и последовательности вместо маски, 0/−inf
  считаются внутри тайла. Сделана ровно под Qwen35, D256, Ampere, f16/q8_0
  KV ([2x4ever#7][maskcompact]).

**Выход.** У битовой маски — побитово тот же; проверить эталонами 8/8.

**Как проверять.**
1. **Фильтр.** `GGML_SCHED_DEBUG=2 -lv 4` на рабочей конфигурации: размер
   `attn_inp_kq_mask` и его копии в CUDA-буфере.
2. **Косвенный тест без кода.** `-c 65536` (маска 512 MiB) и K=3: если K=3
   перестаёт пейджить и даёт prefill не хуже PF-04, механизм подтверждён.
3. Порт битовой маски в форк, свип `tiel-prefetch` с K=2/K=3, эталоны.

  ожидание в цикле. Накладные на запуск падают «с >20 % почти до нуля», и

**Как проверять.** Фильтр — микробенчмарк на этой машине, по образцу
`bench/h2d_bw.cu`. Сравнить круг «ядро → D2H 8 КБ → sync → H2D 64 КБ →
ядро» с кругом «ядро пишет в mapped-память и флаг → CPU ждёт в цикле → CPU
пишет и ставит флаг → ядро-спинер». Если первый ~90 мкс, а второй
≤ 10 мкс — делать (b). Если разница меньше 30 мкс на круг — закрыть.

у него свои:
- KV для слоя MTP, ~136 MiB при q8_0;

## Ранг 17 · №28. Два тракта к DDR4: CPU и DMA по PCIe

**Посылка.** Допустим, DRAM отдаёт ~45 ГБ/с, а ядра CPU берут ~35. DMA с
карты (6.5 ГБ/с) идёт через IO-хаб, а не через фабрику CCX, и может читать
параллельно. Тогда GPU возьмёт на себя 1 эксперта из 8 в каждом слое. Его id
GPU знает первым — роутер считается на GPU. Заливка 1.83 MiB занимает
≈ 0.28 мс и укладывается в окно, пока CPU считает остальные 7 экспертов
(0.38 мс). Это тот же механизм, что у HybriMoE на декоде.

**Расчёт.** CPU-часть 17.5 → ~15.3 мс, **+7 % TG** — если CPU не теряет
полосу от DMA.

**Как проверять.** Фильтр на полчаса: чтение памяти 6 потоками отдельно, а
затем одновременно с циклом `bench/h2d_bw.cu`. Если сумма превышает чтение в
одиночку на ≥ 4 ГБ/с — механизм есть.

**Риск.** Реализация тяжёлая. DMA из pinned-памяти требует `cudaHostRegister`
на все 18 GiB экспертов — те же опасения, что с `--mlock`.

## Ранг 20 · №31. Страничные ошибки под давлением памяти

**Посылка.** С `--load-mode none` эксперты занимают 19.3 GiB обычной,
подкачиваемой памяти на машине с 28 GiB. Когда рядом работают браузер и IDE,
Windows урезает рабочий набор процесса, и страницы экспертов возвращаются
через мягкие, а то и жёсткие ошибки. 586 MiB на токен — это 150 тыс. страниц,
и даже 1 % ошибок по ~2 мкс — уже ~3 мс.

**Как проверять.** Счётчики «Ошибок страницы/с» и «Рабочий набор» процесса
`llama.exe` (perfmon или Process Explorer) во время TG при обычной фоновой
нагрузке. Если ошибки есть — `--load-mode mlock` с оглядкой на прошлый опыт
с `--mlock` или `SetProcessWorkingSetSize`.

**Попутный замер (2026-10-03, №24, `bench/host_mem_log.ps1`,
`bench-logs/tiel-no24-fork-pp/hostmem.csv`).** Сервер Tiel без спекуляции на
форке, `-c 32768 -ub 4096`: private bytes до **27.8 GiB**, рабочий набор
19–21 GiB, системный commit **44.9 из 46.9 GiB** лимита; пик файла подкачки с
загрузки системы — 14 GiB. Сверх 19.3 GiB экспертов ~8 GiB неизвестного
происхождения (кандидаты: prompt cache `--cache-ram`, учёт выделений WDDM) —
**не разобрано**. Давление памяти у машины, похоже, уже есть.

**Разобрано 2026-10-03** (MEM-01…05 в журнале CLAUDE.md, `bench/proc_commit.py`):
4.0 GiB — подложка VRAM (на WDDM `cudaMalloc` коммитит столько же памяти
хоста, в RAM она не лежит), 3.16 GiB — `context_buffer` планировщика,
выделенный под 163 840 узлов при 3953 настоящих и почти не тронутый (→ №44),
~1.1 GiB — настоящая RAM (pinned-буфер, контрольные точки, prompt cache).
Физически сервер занимает ~20.5 GiB, остальное — только commit. Давление на
**физическую** память создаёт prompt cache: лимит по умолчанию 8 GiB, и уже
после трёх промптов (1 GiB кэша) Windows отобрала у экспертов 498 MiB
рабочего набора (→ №45). Сама №31 (ошибки страниц во время TG) этим не
проверена — нужны счётчики, как в плане выше.

## Ранг 21 · №32. HAGS (аппаратное планирование GPU) вкл./выкл.

**Посылка.** Задержки отправки команд и синхронизаций на WDDM — главная
часть накладных 3.9 мс. HAGS меняет путь отправки работы на GPU. По
непроверенным сообщениям он ещё и уменьшает резерв VRAM, который держит
WDDM. Для CUDA-нагрузки с 41 кругом на токен эффект неизвестен ни в одну
сторону.

**Как проверять.** Пользователь переключает «Планирование графического
процессора с аппаратным ускорением» и перезагружается. Затем микробенчмарк
круга из №23, TG и prefill. Дёшево.

## Ранг 22 · №33. Слитый gate_up экспертов: перекладка GGUF без потерь

**Посылка (код).** Загрузчик форка для qwen35moe принимает слитый
`ffn_gate_up_exps`, если он есть в GGUF
([llama-model.cpp:3398](../llama-tiel/src/llama-model.cpp:3398)). У нас
gate и up раздельные. Перекладка — те же байты Q4_K, просто строки gate и up
одного эксперта идут подряд. Квант тот же, так что правило 1 не нарушается.

**Расчёт.**
- **CPU.** На токен на 40 `MUL_MAT_ID` и барьеров меньше, вход квантизуется
  один раз, на эксперта идёт один поток чтения: +1…2 % TG.
- **Prefill.** Матрица эксперта становится 1024×2048 вместо 512×2048, а у
  №13 проблема именно в узости: ~−0.7 с счёта на 28K.
- **Минус.** Слитый тензор весит 362 MiB, больше слота предзаливки (210).
  Каждый слот подорожает, и K=2 обойдётся на ~300 MiB VRAM дороже, если не
  научить предзаливку возить его половинами.

**Как проверять.** Python-скрипт на `gguf` склеивает тензоры. Проверить
загрузку и эталоны (8/8 побитово), затем `llama bench` TG. Prefill — после
решения со слотами.

## Ранг 23 · №34. Перепакованные эксперты (CPU_REPACK) для малых батчей и TG

**Посылка (код + лог).** Сборка собрана с `REPACK = 1`, и в ней есть
AVX2-ядра gemv/gemm 8x8 для Q4_K, Q5_K и Q6_K, в том числе для `MUL_MAT_ID`
([repack.cpp:4937](../llama-tiel/ggml/src/ggml-cpu/repack.cpp:4937)). Но
эксперты лежат в обычном `CPU model buffer`, и перепаковка не используется.
Причина понятна: перепакованный буфер не хостовый, и op offload не сможет
везти такие веса на GPU для prefill.

**Как проверять.**
1. **Фильтр.** `llama bench -ngl 0`, всё на CPU, с перепаковкой и с
   `--no-repack`, `-p 16,32,64 -n 32`. Это покажет выигрыш ядер на TG и на
   малых батчах.
2. **Только если** на малых батчах ≥ 1.5× или на TG ≥ 5 %: перепакованные
   эксперты плюс распаковка на GPU при заливке для prefill. Это лишний буфер
   и лишний проход по 18 GiB на ubatch — тяжело.

## Ранг 24 · №35. `--poll` и режим ожидания CUDA на Tiel

**Посылка.** Между CPU-сплитами потоки ждут GPU ~0.3 мс. Если `--poll 50` не
дотягивает, потоки засыпают, и 41 пробуждение на токен стоит десятки

**Как проверять.** Свип `--poll 50/100` вперемежку ×3, `--tests tg`. Режим
CUDA — одна строка в форке.

## Ранг 25 · №36. Плотный Q8_0 на prefill: cuBLAS против MMQ

## Ранг 26 · №37. Черновик во время CPU-фазы (как PEARL)

**Посылка.** GPU простаивает 17.5 мс на токен, пока CPU читает экспертов.
Драфтер, резидентный в VRAM (DFlash, 401 MiB), мог бы в это время готовить
следующий блок черновика, считая текущий принятым. Это идея PEARL: черновик
идёт параллельно верификации. Упирается в VRAM (G17) и в сложность.
Браться, только если №16 или №24 покажут, что спекуляция у нас окупается.

**Уточнено 2026-10-03 (G17, DF-09…22):** драфтер с лимитом логитов стоит
~1.6 GiB VRAM и на `-c 131072` рядом с Tiel не помещается вовсе; на 32K он
не обгоняет ngram n-max 4. Резидентного драфтера для этой идеи на 6 GiB нет.

## Ранг 28 · №43. Резерв планировщика на каждом запросе без грамматики

*Добавлена 2026-10-03 по итогам №18 (FL-01…10 в журнале CLAUDE.md).*

**Посылка (замер + код).** С `--backend-sampling` каждый запрос без грамматики
платит полный `sched_reserve`: 0.29–0.31 с на 131K/4096, 0.05–0.10 с на
32K/1024. `llama_set_sampler()` ставит `sched_need_reserve` и при регистрации
сэмплера, и при сбросе в `nullptr`
([llama-context.cpp:1282–1337](../llama-tiel/src/llama-context.cpp:1282)), а
сервер делает и то, и другое на каждом запросе. Резерв пересоздаёт
планировщик и строит худший граф на `n_ubatch` токенов против полного KV.
Агентный клиент шлёт грамматику и не платит.

**Кому это важно.** Харнессам: все floor-числа включают резерв, то есть
меряют не то, что видит агент. Голому чату и Gemma (G21 в журнале).

**Варианты** (выход не меняется ни в одном):
1. **Снять `--backend-sampling` в лаунчере.** 0 работы. Ход без грамматики
   −0.15…0.35 с, его генерация −1.5 % (FL-06…08); окупается при ответе
   короче ~600 токенов. Агенту — ничего.
2. **Харнессы шлют `backend_sampling: false`** (или грамматику), чтобы floor
   мерил то, что видит агент. Ломает сравнимость floor со старыми строками —
   нужна новая точка отсчёта.
3. **Патч `set_sampler`**: не резервировать заново, если сэмплер того же
   вида уже был в графе, а при сбросе не трогать резерв. Сохраняет +1.5 % TG
   и убирает 0.3 с. Риск — граф сэмплера меняет число узлов, и резерв без
   него может не покрыть буферы; проверять `GGML_SCHED_DEBUG` и эталонами.
   Сначала поискать в апстриме после `dcd387a41`.

**Фильтр.** Решение пользователя по варианту 1; для варианта 3 — поиск в
апстриме и дамп буферов до и после.

## Ранг 29 · №44. `context_buffer` планировщика по настоящему графу

*Добавлена 2026-10-03 по итогам разбора памяти (MEM-01…05, раздел «№31,
попутно» в журнале CLAUDE.md).*

**Посылка (замер + код).** `ggml_backend_sched_new` делает `malloc` на
`graph_size × 30 × 2 × sizeof(ggml_tensor)` под тензоры входов сплитов
([ggml-backend.cpp:2234](../llama-tiel/ggml/src/ggml-backend.cpp:2234)), а
`graph_size` для `qwen35moe` = `max(40 × n_ubatch, 32 × n_tensors)`. На
ub 4096 это 3.16 GiB commit (ub 2048 — 1.58, ub 8192 — 6.3 по расчёту), из
которых тронуто 0.14 MiB: в графе 3953 узла и 122 сплита. В RAM не лежит, но
занимает лимит commit и растит файл подкачки. Второй контекст той же
архитектуры (draft MTP) резервирует ещё столько же — вероятная причина
`bad allocation` у MTP-сервера на форке (№24: commit 50.5 из 46.9 GiB).

**Что сделать.** Выделять `context_buffer` лениво в `split_graph` по
настоящему `graph->n_nodes` (и расти при необходимости), либо ограничить
число входов реальным числом сплитов. Скорость не меняется: буфер — только
метаданные тензоров.

**Фильтр.** Патч в форке, `proc_commit.py` до/после, эталоны 8/8 побитово.
Затем — стартует ли MTP-сервер, падавший по памяти хоста. Сначала поискать
в апстриме после `dcd387a41`.

## Ранг 30 · №45. Лимит `--cache-ram` ниже 8 GiB

*Добавлена 2026-10-03 по итогам разбора памяти (MEM-04).*

**Посылка (замер).** Prompt cache сервера хранит состояния простаивающих
слотов в настоящей RAM, лимит по умолчанию — 8192 MiB. Состояние на 28K
токенов q8_0 — 356 MiB плюс контрольные точки по 62.8 MiB: три промпта дали
1025 MiB кэша, и Windows уже отобрала у экспертов 498 MiB рабочего набора. При
20.5 GiB сервера на 28 GiB машины кэш, выросший до 8 GiB, вытеснит экспертов,
и TG станет платить ошибками страниц (№31).

**Цена.** Кэш экономит повторный prefill при возврате к другой беседе; с
одним агентом и `-np 1` это редкий случай, но подагенты и параллельный чат
его создают.

**Фильтр.** После N разных длинных промптов: рабочий набор экспертов
(`proc_commit.py`), ошибки страниц и TG при 8192 против, например, 2048 MiB.

## Ранг 31 · №46. Шаблон: `\n\n` между параллельными вызовами инструментов

*Добавлена 2026-10-03 по итогам №19 (PA-03, ход #14).*

**Посылка (замер).** Модель написала три параллельных вызова `read_file`,
разделив `</tool_call>` и `<tool_call>` токеном 271 (`\n\n`). Шаблон из GGUF
(`qwen3.8-froggeric-v22.4.0`, ветка xml) при перерисовке ставит между
вызовами `'\n<tool_call>…'`, то есть токен 198 (`\n`). Префикс рвётся внутри
прошлого ответа, сервер откатывается к точке за 4 токена до конца прошлого
промпта и пересчитывает ответ целиком: 221 токен на этом ходе.

**Метод.** Свой файл шаблона (`--chat-template-file`, из GGUF с одной
правкой: `'\n<tool_call>'` → `'\n\n<tool_call>'` для второго и следующих
вызовов в xml-ветке), передавать лаунчером. Сборка не нужна.

**Цена.** На ходах после параллельных вызовов — весь прошлый ответ (сотни
токенов). На коротком следующем ходе это ~1.5–2.5 с: лишние токены
перебрасывают его через порог 128 на путь с заливкой экспертов. На
длинном (≥ ~1000 новых) — почти ноль.

**Выход.** Модель видит в истории ровно то, что сама написала; на
эталонах `tiel_reference` (там нет вызовов) — побитово.

**Фильтр.** Один случай — не правило. `prefix_audit.py` с задачами, которые
провоцируют параллельные вызовы, на стоковом шаблоне: всегда ли модель
пишет `\n\n`. Если всегда — правка шаблона и тот же прогон с ней: потери на
таких ходах должны стать 0.

## Ранг 32 · №47. Совпадение префикса по тексту, а не по id токенов

*Добавлена 2026-10-03 по итогам №19 (PA-01, PA-03, ход #7).*

**Посылка (замер).** Модель сгенерировала `<parameter=path>` токенами
`27 15704 28 2267 29` (`<`, `parameter`, `=`, `path`, `>`), а токенизатор
на перерисовке склеивает `=path` в 79114. Текст тот же побайтово, но
`server_tokens::get_common_prefix`
([server-common.cpp:697](../llama-tiel/tools/server/server-common.cpp:697))
сравнивает id, и ход пересчитывает прошлый ответ: 93 токена. 1 ход из 26.

**Метод.** Если общий префикс кэша и нового промпта кончается внутри
сгенерированной части кэша, сравнить хвосты по тексту: если
детокенизированный хвост кэша — префикс нового промпта и кончается на
границе его токенов, взять токены кэша и дотокенизировать только остаток
(спаны сообщений пересчитать). Вход модели становится теми токенами,
которые она сама написала, — как если бы беседа шла без перерисовки.

**Цена.** Лёгкая-средняя, патч в сервере форка. Выигрыш — как у №46, но
реже (1 из 26 ходов на этой сессии). Сначала поискать в апстриме.

**Выход.** На затронутых ходах вход меняется на неканоничные токены (ближние
ничьи); без расхождения — побитово.

**Фильтр.** Частота на длинной сессии с настоящим клиентом; если меньше
~1 хода из 20 и ходы после них длинные — не делать.

## ~~Ранг 33~~ · №48 (проверена, опровергнута). Маска потоков без логического CPU 0

> Но `MUL_MAT_ID`/`MUL_MAT` на CPU раздают куски через атомарный счётчик

**Фильтр.** `llama bench` TG (рабочие флаги Tiel, `-n 128 -r 5`) `-C 555`

## Рассмотрено при поиске и отброшено арифметикой

- **Голова вывода внахлёст с экспертами последнего слоя через линейность:**
  logits = W′(a + s) + W′·m. Нужен второй полный матвек по 515 MiB, выигрыша
  нет.
- **CPU как сопроцессор экспертов на большом prefill (≥ 1024).** На батчевом
  Q4_K CPU даёт ~0.1 TFLOPS (по H2-crossover: ~125 GFLOPS на 150–415
  токенах), GPU — 7–10. Максимум 1–3 %.
- **Сжатие весов без потерь для шины и DDR4.** У Q4_K энтропия почти
  максимальна; схемы вроде DFloat11 работают для BF16.
- **iGPU для экспертов в TG.** Он делит ту же DDR4, что и так на пределе —
  разве что №28 покажет запас у DRAM.
- **Предвычислить слой 0 следующего токена по кандидатам.** Выигрыш
  ~0.3 мс × вероятность угадать.
- **Pinned-память под экспертов для TG.** В TG экспертов читает CPU, шина не
  участвует.
- **Постоянная f16-копия KV для пакета проверки (к №39), с переводом только
  новых строк.** Перевод на раунд исчез бы, но копия на `-c 131072` весит
  2.6 GiB (KV 1360 MiB при q8_0) — в 6 GiB карты не влезает
  (2026-10-03).
- **Self-speculation, LayerSkip, Lookahead/Jacobi.** Черновик сам стоит доли
  токена с теми же экспертами на CPU, а верификация на CPU линейна по
  токенам. При нулевой цене ngram-черновика (№16) смысла нет.
