# MOE-VIABLE-HYPOTHESES.md — рабочие гипотезы ускорения MoE, по приоритету

**Назначение.** Здесь перечислены гипотезы ускорения MoE в связке CPU RAM +
GPU VRAM, которые не закрыты замером или арифметикой. Они отсортированы так,
чтобы проверять их **сверху вниз**.

**Новый пул (2026-10-02):** №16–№38 собраны отдельно, в
[MOE-NEW-HYPOTHESES.md](MOE-NEW-HYPOTHESES.md). Проверенные оттуда переносить
сюда или в отклонённые, номера сохраняются.

**Пересмотрено 2026-10-01.** Посылки сверены с журналом [CLAUDE.md](../CLAUDE.md)
и [TUNING.md](TUNING.md). Главные ошибки прежней редакции:

- Шапка смешивала модели: 33.8 t/s, 29.8 мс на токен и 10.7 мс GPU сняты на
  **Gemma**, а 25.94 мс «простоя GPU» — стена, раздутая профилировщиком.
- Все прогнозы «до 45–62 t/s» считались от Gemma-овских 33.8 t/s и делили на
  новый объём **весь** токен, хотя GPU-часть от числа экспертов не зависит.
- Гипотезы с VRAM-кэшем рассчитывали на 2.5 ГБ свободной VRAM. У Tiel её
  ≤ 929 MiB.
- Префетч экспертов через PCIe считался на Gen3 x8 «почти бесплатным». На деле
  промахи стоят десятки миллисекунд на токен (см. №8).

Две гипотезы добавлены: №2 (что на самом деле стоит prefill) и №4 (префетч
в L3 вместо PCIe — переформулировка Pre-gated MoE под это железо).

**Порядок сортировки** (2026-10-01). Сначала все гипотезы, которые **не
меняют** выход модели, потом все, которые меняют, — независимо от размера
выигрыша. Внутри каждой группы ранг — вероятность получить **измеримый**
выигрыш на этом стенде; при равных шансах выше то, что проверяется без
пересборки. «Измеримый» значит больше внутрисвипового разброса TG: два
baseline одного свипа расходятся на 1.6–4 %, между свипами — до 9 %. Каждый
свип начинается и заканчивается baseline (протокол CLAUDE.md).

**Номер (№) — постоянный идентификатор, ранг — порядок проверки.** На номера
ссылаются журнал и [MOE-REJECTED-HYPOTHESES.md](MOE-REJECTED-HYPOTHESES.md),
поэтому при пересортировке они не меняются. Разделы ниже идут по рангу.

Пометки: **замер** — есть строка в журнале; **расчёт** — арифметика, то есть
гипотеза по правилу 2; **не проверено** — взято из статьи или чужого issue.

## Ранг 1 · №3. `-np 2`: суммарная пропускная способность для двух клиентов

**Что было неверно.** Прежняя редакция описывала «Dual-Batch Interleaving»:
пока CPU считает MoE запроса A, GPU считает аттеншн запроса B, и это «без роста
индивидуальной задержки». llama.cpp так не умеет — с двумя слотами она
**склеивает** токены обоих запросов в один батч. Индивидуальная скорость при
этом падает. Ссылку на OSDI '26 не проверяли.

**Расчёт склейки** (от профиля шага 0). Плотная часть на GPU читается один
раз на оба токена. Экспертов при независимой маршрутизации — 15.75 вместо 8,
CPU-часть растёт в ~1.97 раза. Шаг ≈ 17.5 × 1.97 + 12.2 + 3.9 ≈ 50.6 мс на два
токена:

- суммарно ~39.5 t/s против 29.8, **~+33 %**;
- на каждый поток ~19.8 t/s, **~−34 %**.

**Когда это нужно.** Только при двух одновременных клиентах (агент плюс
субагент, два чата). Для одного пользователя это минус.

**Как проверять.** Сборка штатная. `-c 131072` делится между слотами —
посмотреть `--kv-unified` / `--kv-unified-per-slot` в `--help`.
`sweep_bench.py` шлёт запросы последовательно, нужен тест на два одновременных
`tg`-запроса с суммой t/s.

## Ранг 2 · №9. Перекрытие shared-эксперта на GPU с routed на CPU

**Что было неверно.** «1.6 мс, +5–7 %» — это G14, плотный MLP **Gemma**
в 23 слоях.

**Расчёт для Tiel** (от профиля шага 0). shexp — 127.2 MiB на токен, ~0.6 мс
при измеренных 216.7 MiB/мс, **~+1.8 %**. Ниже шума TG.

**Почему почти безнадёжно.** Как показано в G14, перестановки веток в графе
мало: хост всё равно ждёт весь предыдущий CUDA-сплит. Нужен look-ahead в
`compute_splits`, который ломает защиту переиспользования буферов аллокатором.
За 2 % — не сделка. Имеет смысл, только если №4 уже требует look-ahead. (№4 закрыта 2026-10-02 без look-ahead — этот довод отпал.)

## Ранг 3 · №14. Ядро GatedDeltaNet на prefill

> **2026-10-03:** готовое ядро из PR #26001 проверено как №26
> (CLAUDE.md «№26»): ядро ×2.9, но prefill с предзаливкой упирается в шину,
> и до стены доходит +2.8 %. Писать своё ядро имеет смысл только вместе с
> возвратом №12 — условие ниже подтвердилось замером.

**Добавлена 2026-10-02** по профилю ядер prefill
([bench-logs/moe-batch/results.md](../bench-logs/moe-batch/results.md)):
`gated_delta_net_cuda` — 3.43 с из 15.87 с счёта на 28K, 22 %, 14.3 мс на
слой × ubatch из 4096 токенов (30 рекуррентных слоёв). Апстрим после базы
форка (21 коммит до `8d81559fa`) ядро не трогал.

**Связка с №12 — главное условие.** После №7 prefill на ubatch ≈ max(заливка
~3 с, счёт ~3 с): заливка прячется за счётом и наоборот. Ускорение одного
счёта упрётся в заливку, а layer-centric (№12) один дал +3.5 %, потому что
упёрся в счёт. Выигрыш ядра окупится только с вернувшимся №12
(`patches/tiel-layer-centric.patch`).

**Как проверять.** Сначала потолок: байты и FLOP ядра на одном вызове
(состояние 128×128 на голову, чанки) против 224 MiB/мс и тензорных FLOPS
карты. Если ядро уже у потолка — закрыть арифметикой. Если далеко — Nsight
Compute по одному запуску (`test-backend-ops perf -o GATED_DELTA_NET` с
формой Tiel), где стоит.

## Ранг 4 · №13. `mul_mat_q` на узких экспертах Tiel

**Добавлена 2026-10-02** микробенчмарком `test-backend-ops perf`
([bench-logs/moe-batch/results.md](../bench-logs/moe-batch/results.md)).

**Что измерено.** Эксперты — 28 % счёта prefill (4.46 с из 15.9 на 28K).
`MUL_MAT_ID` на формах Tiel идёт на 6–10 TFLOPS при любом типе (Q4_0…Q6_K,
Q8_0) и при любом числе токенов от 1K до 16K. Та же операция на форме Gemma
(1408×2816) — 14–18, плотный Q8_0 — 30.7. Путь через f16 хуже вдвое (3.5).
То есть мешает форма: матрица эксперта 512×2048, у down k = 512.

**Что отпало.** «Посчитать MoE слоя сразу на нескольких ubatch, чтобы у
эксперта было больше строк» — для Tiel не работает (см. отклонённые, п. 16).

**Приз** (расчёт). Если довести экспертов до уровня формы Gemma (~15 TFLOPS),
4.46 → ~2.5 с, −1.9 с счёта на 28K. **Окупается только вместе с №12**, по той
же причине, что №14.

**Как проверять.** Nsight Systems по `test-backend-ops perf` с формой Tiel:
какая доля `MUL_MAT_ID` — сам `mul_mat_q`, а какая — `quantize_mmq_q8_1`,
`mm_ids_helper` и `stream_k_fixup`. Если время в обвязке — её и резать; если
в самом ядре — подбор тайлов `mmq` под m = 512 / k = 512.

## Ранг 5 · №11. Спекуляция только по резидентным экспертам (EcoSpec / DraftExpert)

**Мерить не нужно, кандидат на перенос в отклонённые.**

- У Tiel резидентных экспертов **ноль**: ни одного слоя на GPU при любом
  контексте. Ограничивать черновик нечем.
- У Gemma 7 слоёв лежат на GPU целиком, а 23 — целиком на CPU. «Резидентность»
  там по слоям, а не по экспертам, и любой черновик проходит через все 23
  CPU-слоя.
- Спекуляция на Tiel и так отклонена из-за prefill (отклонённые, п. 1), и это
  ограничение причину не устраняет.

Оживает, только если №8 будет реализован и даст заметную долю резидентных
срезов.

## Ранг 6 · №1. Меньше экспертов на токен (статический top-k → динамический top-p)

**Суть.** CPU читает только выбранных экспертов, поэтому время CPU-части
пропорционально их числу. Резать можно статически (top-k меньше 8) или
динамически: брать экспертов по убыванию веса, пока сумма весов не достигнет P.

**Что было неверно.**
- Прогноз «45–52 t/s» считался от Gemma-овских 33.8 и уменьшал весь токен,
  а не только CPU-часть.
- Гипотеза стояла под шапкой «без ухудшения модели». Но она **меняет
  вычисление**, и это надо мерить как изменение качества.
- «Среднее число экспертов падает до ~4.5 при P = 0.9» — чужое число, на Tiel
  не проверено.

**Расчёт** (от профиля шага 0). CPU 17.5 мс, пропорционально k. Остальное
(16.1 мс) не меняется.

| k | CPU, мс | токен, мс | TG | Δ |
|---|---|---|---|---|
| 8 | 17.5 | 33.6 | 29.8 | — |
| 6 | 13.1 | 29.2 | 34.2 | +15 % |
| 5 | 10.9 | 27.0 | 37.0 | +24 % |
| 4 | 8.75 | 24.9 | 40.2 | +35 % |

**Почему не первая.** Скоростная половина почти гарантирована физикой, а
первый шаг не требует ни строчки кода. Но гипотеза меняет выход модели, а с
2026-10-01 все такие гипотезы стоят ниже тех, что качество сохраняют. Внутри
своей группы она первая.

**Как проверять.**
1. Статический k без пересборки:
   `--override-kv qwen35moe.expert_used_count=int:6` (ключ сверен по заголовку
   GGUF, флаг есть в `--help`). Свип baseline → k = 7, 6, 5, 4 → baseline,
   протокол как обычно (`-c 131072 -ctk q8_0 -ctv q8_0`). В лог-файле проверить,
   что `n_expert_used` действительно стал 6. Если загрузчик берёт k не из этого
   ключа, флаг ничего не изменит.
2. Качество. `kv_quality_test.py` годится только для Gemma и KV-типов, нужна

## Закрыта · №4. Раннее предсказание роутера + префетч экспертов в L3

> **Опровергнута 2026-10-02 патчем в форке и свипом на сервере** (бывший ранг 3,
> журнал — CLAUDE.md, L3-01…10; разбор — [MOE-REJECTED-HYPOTHESES.md](MOE-REJECTED-HYPOTHESES.md), п. 14).
> Механизм работает: эксперты слоя 396 → 341 мкс. Но помощники растягивают
> окно 329 → 355 мкс, и на токен остаётся ~1 мс: +1.1 % TG за 9 пар выкл./вкл.,
> вне шума не выходит. Патч снят (ветка форка `rejected/no4-l3-prefetch`).
> Ниже — разбор до патча, как он был.

**Переформулировка Pre-gated MoE / SpecPrefetch.** В исходном виде гипотеза
предлагала досрочно запускать DMA по PCIe — на x8 это мёртво (см. №8). Но у
идеи есть применение на этом железе.

**Посылка (замер, Gemma).** CPU и GPU работают строго по очереди. Пока
GPU считает аттеншн и плотное (~10 мс на токен), **DDR4 простаивает**, потому
что потоки CPU ждут GPU. Пока CPU читает экспертов (~16 мс), простаивает GPU.

**Идея.** Пока GPU считает аттеншн слоя L, предсказать экспертов слоя L по
входу x_L и **прочитать их веса в L3** (16 МБ). Тогда MoE на CPU возьмёт их
из кэша, а не из DDR4. Выход остаётся побитово точным: настоящий роутер
работает как обычно, при промахе эксперт читается из DDR4.

**Посылка подтверждена на Tiel** (шаг 0, S0-03): 41 CPU-сплит и 41 CUDA-сплит
на токен строго чередуются, хост ждёт GPU 12.2 мс из 33.6. Сплиты слоёв не
склеены — окно есть на каждом слое.

**Расчёт** (от профиля шага 0). Эксперты одного слоя — 14.66 MiB, это почти
весь L3 (16 МБ = 15.26 MiB). Чтение — **0.44 мс** при измеренных 33.5 MiB/мс.
GPU-окно на слой — **0.25–0.33 мс** (10.1 мс ожидания на 41 сплит; 13.06 мс
ядер на 40 слоёв). Спрятать можно 57–75 % чтения каждого слоя: **потолок
10–13 мс из 17.5**, то есть токен 33.6 → ~21–24 мс. Потолок считает, что
счёт по данным из L3 ничего не стоит и предсказание безошибочно, — ни то ни
другое не измерено. С точностью досрочного роутера 82–91 % (чужое число,
**не проверено**) и вытеснением из L3 реалистичная оценка прежняя: **~+20 %**.

**Риски.** Слой едва помещается в L3, и рядом живут активации. Префетч на
Windows из отдельного потока при `--cpu-strict 1` и маске 555 нужно встроить
в `compute_splits`.

**Как проверять, по шагам и с выходом на каждом.**

   пройден, см. ниже.
3. ~~Синтетика: время matvec по 14.66 MiB, прочитанным заранее в L3, против

   трогая llama.cpp.~~ Сделано: выигрыш есть, но втрое меньше расчётного.

### Шаги 2–3 сделаны (2026-10-01): приз ~2 мс на токен, а не 10–13

Инструменты, строки запуска и сырые числа —
[bench-logs/no4-l3/results.md](../bench-logs/no4-l3/results.md), журнал —

**Расчёт.** Если №2 подтвердит полный стриминг на каждый ubatch: 7 × 19.7 ГБ ≈
138 ГБ против 19.7 при загрузке каждого слоя один раз, ~21 с → ~3 с из 37.8.
Prefill 28K токенов ~38 → ~20 с.

**Цена.** Это переписывание порядка выполнения в llama.cpp: KV и активации всех
ubatch промпта на слое, затем следующий слой. Дешёвая промежуточная проба —
`-ub 8192`, если compute-буфер влезет в VRAM.

> Ниже — исходная формулировка.

**Добавлена 2026-10-02** по трассам роутера из проверки №8
([bench-logs/no8-hot/results.md](../bench-logs/no8-hot/results.md)).
Статический набор провалился потому, что перекос у каждого текста свой: на
русской прозе эксперты слоя сжимаются до exp(H) 92 из 256, на генерации
кода — 153, и наборы почти не пересекаются. Зато внутри одной генерации
перекос держится сотни токенов.

**Механизм.** В VRAM лежит набор срезов экспертов (бюджет как у №8). Каждые
W токенов хост пересобирает набор по частотам последних W токенов — id
экспертов и так приходят на CPU каждый слой, счётчики бесплатны — и
перезаливает только новые срезы вторым CUDA-потоком (инфраструктура №7).
Это не кэш с подкачкой промахов (отклонённый п. 7: ~80 мс на токен), а
медленно дрейфующий набор: промахи по-прежнему считает CPU.

**Расчёт** (по трассам, набор из прошлых W токенов, проверка на следующих W):

| бюджет | 84 MiB | 446 MiB | 656 MiB | 929 MiB |
|---|---|---|---|---|
| попадания, W=256 | 5.8 % | 18.4 % | 22.9 % | 27.7 % |
| шина, мс/токен | 0.03 | 0.13 | 0.20 | 0.29 |
| TG сверху | +2.6 % | **+8.8 %** | +11.2 % | +13.9 % |

На агентном случае (`gen-review`, разбор чужого модуля) попадания ниже —
11.7 % на 446 MiB, ~+5.5 %. Оценка сверху: не учтены неравномерная раздача
экспертов потокам CPU и лишние запуски ядер на GPU.

**Как проверять.** Сначала дешёвый фильтр без GPU-части: нужен ли вообще
линейный выигрыш на CPU. Патч в `ggml-cpu` `MUL_MAT_ID`: пропускать id из
маски (выход не тот, но время CPU-части при 7.3 эксперта из 8 вместо 8
измеримо в `llama bench`). Если CPU-часть не падает пропорционально байтам —
закрыть. Затем полная реализация: на GPU `MUL_MAT_ID` по набору с
переадресацией id (холодные → пропуск), на CPU — пропуск горячих, сумма
двух частей на GPU, двойной буфер набора и счётчики на хосте.

**Бюджет VRAM — главный риск.** 446 MiB — это q8_0 + ub 4096 с K=2. У
лаунчера по умолчанию (f16, ub 2048, K=1) запас 84 MiB, и тогда приза нет
(+2.6 %). Большие бюджеты (1500–2100 MiB, +17…23 %) есть только на время
генерации — compute-буфер ubatch 4096 и слоты предзаливки на ней
простаивают, — но их пришлось бы перезаливать после каждого длинного
prefill (~0.2–0.3 с) и делить с аллокатором.
